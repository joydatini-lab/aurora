## Le défaut réel trouvé (et corrigé) — G8
`resolveThemeCSSVars` émettait `--aurora-${key}` en gardant le POINT des clés de
token : `--aurora-accent.primary`, `--aurora-text.primary`. Or TOUT le dépôt lit
la forme TIRET : `styles/aurora.css`, les CSS d'`apps/mobile`, et `toShadcnVars`
lui-même (`g("--aurora-accent-primary")`).

Conséquence : `--primary`, `--accent`, `--secondary` n'étaient JAMAIS définis par
le provider. L'état actif de la navigation était transparent.

Pourquoi personne ne l'avait vu : `apps/mobile/src/main.tsx` charge
`styles/tokens.css`, un bloc `:root` de replis qui définit tous les noms TIRET.
Le défaut était donc masqué sur mobile. `apps/web-app` n'a pas ces replis → il
l'a exposé immédiatement.

Correctif : `key.replace(/\./g, "-")`. Mesure : `--accent` passe de `""` à
`#B8DFFF`, `background-color` de `rgba(0,0,0,0)` à `rgb(184,223,255)`.

**Leçon** : un nom de variable CSS est une interface entre deux fichiers. Quand
l'émetteur et le lecteur divergent, RIEN ne lève d'erreur — la valeur est
simplement vide. Ne jamais conclure d'un nom lu dans le code : mesurer
`getComputedStyle(el).getPropertyValue('--x')` dans le navigateur.

## Le piège Tailwind (deuxième défaut, corrigé avant commit)
Ma première version du `tailwind.config.ts` branchait `presets: [auroraPreset]`.
`packages/ui/tailwind.config.ts` mappe ses couleurs sur des TRIPLETS
(`hsl(var(--aurora-bg-h))`), or le provider écrit les ALIAS SHADCN en valeur
PLEINE (`--background: #fff`). Les triplets `-h` viennent d'`aurora.css`, que
Vite ne charge PAS. Résultat : tout transparent.

La forme qui marche est celle d'`apps/mobile/tailwind.config.js` :
`colors: { background: 'var(--background)' }`. Le shell suit donc cette
convention, et le test interdit le retour d'`auroraPreset`.
