# Aurora — Réévaluation « web-only »

> **Date :** 2026-10-28 · **Branche :** `arena/fa2fed09-aurora` · **HEAD :** `07d70a6`
> **Décision produit (2026-10-28) :** la voie **mobile (Android/Capacitor) est abandonnée** ; la cible est **la voie web**.
> **Portée :** ce document **complète** `docs/analysis/analyse-projet-aurora-2026-10-28.md` (diagnostic complet) et `docs/analysis/analyse-projet-aurora.md` (analyse 2026-10-09). Il ne le remplace pas : les constats de sécurité et de gouvernance restent valides, mais leur **priorité change**.
> **Statut :** le web est un **pivot de cible, pas une réécriture**. Ce qui suit chiffre l'écart réel entre les deux.

---

## 1. L'impact de la décision en une page

Le point contre-intuitif : **Aurora est déjà, à 90 %, une application web.**

| Élément | État réel | Conséquence pour le web |
|---|---|---|
| Routage | `createBrowserRouter` de **`react-router-dom`** (`apps/mobile/src/router.tsx:30`) | ✅ **Standard SPA** — Ionic ne route pas. Rien à refaire |
| Chrome / écrans | 34 fichiers `.tsx` sur 70 utilisent `@ionic/react` (`IonApp`, `IonHeader`, `IonContent`, `IonFooter`, `IonTitle`) | ✅ Ionic est fait de **web components** : rendu navigateur natif |
| Le reste de l'UI | 36 fichiers sur 70 en **shadcn + Tailwind + Radix** | ✅ déjà web |
| `packages/platform` | 4 adapters gardés par `Capacitor.isNativePlatform()` | ✅ **dégradation web déjà écrite** |
| Self-updater APK | `useUpdater` : `getPlatform() !== 'android'` → `idle` pour toujours | ✅ **no-op web déjà conçu** |
| Moteur de données | `@powersync/web` **déjà déclaré** (`packages/data/package.json`) mais **jamais importé** | ⚠️ 1 fichier à basculer |
| Sync point d'injection | `createPowerSyncClientEngine(options, dbFactory?)` **existe déjà** (`powersync-client.ts:325`) | ✅ le seam est prévu |
| PWA | **aucun** `manifest.json`, aucun service worker (`apps/mobile/public/` ne contient que `themes/`) | ❌ à créer |

**Conclusion :** le pivot web coûte **4 correctifs de code** et un pipeline de déploiement. Ce n'est **pas** un projet de migration — c'est un débranchement.

## 2. Les 4 blocages réels du web (avec `fichier:ligne`)

### 🔴 B1 — `@capacitor/preferences` casse le bundle

```
[vite]: Rollup failed to resolve import "@capacitor/preferences"
        from "apps/mobile/src/updater/apkUpdater.ts"
```

```ts
// apps/mobile/src/updater/apkUpdater.ts:16   ← import TOP-LEVEL
import { Preferences } from '@capacitor/preferences';
```

Ironie : le module est **parfaitement gardé au runtime** (`Capacitor.isNativePlatform()` aux lignes 132, 170, 190, 223) et `useUpdater` documente explicitement le no-op web. Mais **un import statique non résolu casse le bundler avant tout garde runtime**. Le paquet n'est déclaré nulle part.

**Deux correctifs possibles :**

- *Minimal (5 min)* : ajouter `@capacitor/preferences` aux deps de `apps/mobile`. Le build passe, le code reste no-op sur web. **Dette : un paquet natif dans un bundle web.**
- *Cible (30 min)* : sortir le module du graphe web via un **split de plateforme** (§3.1). Recommandé.

### 🔴 B2 — Le moteur PowerSync est câblé en dur sur Capacitor

```ts
// packages/data/src/powersync-client.ts:21
import { PowerSyncDatabase } from '@powersync/capacitor';   // ← import de VALEUR
```

Le fichier **anticipe déjà** le cas web (ses commentaires lignes 29-31 et 321-322 décrivent « backed by `@powersync/web` (WASQLite) »), et l'injection existe :

```ts
// powersync-client.ts:325
export function createPowerSyncClientEngine(options, dbFactory?: PowerSyncDatabaseCtor)
```

…mais **`boot-data.ts:112` ne la passe pas** :

```ts
const engine = createPowerSyncClientEngine({
  endpoint: env.powersyncUrl,
  createClient: clientFactory,
  dbFilename: env.dbFilename,
});            // ← pas de dbFactory → le défaut Capacitor s'applique
```

Or `@powersync/web` **est déjà une dépendance déclarée** de `packages/data` (jamais importée). Sur navigateur, `@powersync/capacitor` n'offre pas de SQLite utilisable : **la persistance locale (AD-7, offline-first) ne fonctionnerait pas**.

**Correctif :** extraire l'import de valeur dans un module `*platform*`, et passer `PowerSyncDatabase` de `@powersync/web` depuis `boot-data.ts`. **~1 h.** C'est le seul vrai travail de fond du pivot.

### 🟠 B3 — `@capacitor/core` non déclaré dans `packages/platform`

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@capacitor/core'
imported from packages/platform/src/lifecycle.ts
```

Déclaré : `@capacitor/app`, `@capacitor/network`, `@capacitor/push-notifications` — **pas `core`**, alors qu'il est importé par 4 fichiers (`lifecycle`, `local-notification`, `network`, `remote-notification`).

Conséquence : **2 suites de tests rouges** (`platform` 0/1, `focus` 12/1). **Correctif : 1 ligne.**

### 🟠 B4 — Aucune infrastructure web

- **Pas de PWA** : ni `manifest.json`, ni service worker → l'argument central du produit (« offline-first, AD-7 ») n'est **pas tenu sur le web**.
- **Pas de déploiement** : `release.yml` construit une APK (qui, on l'a vu, n'est jamais construite) ; **aucun job n'a jamais publié un site**.
- **SPA fallback** : `createBrowserRouter` exige que l'hébergeur réécrive `/*` → `index.html`, sinon toute URL profonde (`/goals/:id`) renvoie une 404.
- **Secrets de build** : `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_POWERSYNC_URL` (`main.tsx:64-66`) — **injectés au build** dans un bundle **public**. Acceptable pour une publishable key, à condition de ne jamais y mettre de service_role (aujourd'hui respecté ✅).

## 3. Ce que la décision change dans le diagnostic

### 3.1 Ce qui reste prioritaire — et devient **plus** urgent

| Constat | Impact du pivot |
|---|---|
| 🔴 **`fn-dev-auth` non authentifiée** (§5.1 de l'analyse) | **Aggravé.** Une APK se distribue à quelques testeurs ; **un site web est indexable et accessible à tous.** `list-users` + `set-password` sur le projet de prod = compromission de compte à grande échelle. **Bloquant absolu du go-live web.** |
| 🔴 **Identifiants dev en clair** (§5.2) | **Aggravé.** Dans une APK il faut décompiler ; dans un bundle web, `Ctrl+F` dans les DevTools suffit. Et le bundle est **public** par construction. |
| 🟠 **`pnpm lint` ne démarre pas** (§6.1-6.2) | **Inchangé, mais plus critique** : le web expose le code à tous, les frontières AD-1/AD-10 doivent être *tenues par la CI*, pas par discipline. |
| 🟠 **Traçabilité git nulle** (§6.6) | **Plus grave** : un déploiement web continu sans historique = **aucun rollback possible**. |
| 🟠 **Packages vides** (§6.3) | Inchangé. |
| 🟡 **Dette CSS `data.css` 4 442 lignes** | Inchangé (le web la subit autant que le mobile). |

### 3.2 Ce qui devient **caduc**

| Constat | Statut |
|---|---|
| « Le workflow de release ne produit pas d'APK » (§6.4) | **Sans objet.** À remplacer par : *aucun déploiement web n'existe* — même trou, autre cible. |

## 4. Inventaire du code à débrancher (pas à supprimer)

Chiffré, pour mesurer le gain réel — **et parce que « abandonnée » ne veut pas dire « effacée »** : garder le code derrière une frontière propre permet de le réactiver si la stratégie change.

| Élément | Volume | Décision recommandée |
|---|---|---|
| `apps/mobile/src/updater/` (5 fichiers) | **1 008 lignes** | **Isoler** derrière `*.native.ts` (inactif sur web) |
| `packages/platform/src/dpc*.ts` + `boot-receiver.ts` | **235 lignes** | **Isoler** (Android Digital Wellbeing) |
| `apps/mobile/android/` (Gradle, keystore, ressources) | **445 Ko** | **Garder** hors build web ; supprimer du CI |
| `apps/mobile/capacitor.config.ts` | 35 lignes | **Garder** (n'entre pas dans le bundle web) |
| `e2e/device/` + `tests/e2e/` | **565 lignes** | **Retirer du CI** ; remplacer par du Playwright navigateur |
| `apps/desktop/` (Electron) | 61 lignes | **Hors périmètre** (Phase 2 déjà annoncée) |
| 6 fichiers de tests couplés | `focus-dpc`, `updater-config-wiring`, `engine-swap`, `scenarios-s13`, `service`, `platform` | **Retaguer** : 2 deviennent web-pertinents (`engine-swap` ✅, `platform` ✅ après B3), 2 sont mobile-only (`focus-dpc`, `updater-config-wiring`) |
| `release.yml` job `release-build` (APK) | — | **Remplacer** par un build statique + upload |

**Total à isoler : ≈ 1 250 lignes** (sur 35 205 dans `apps/mobile`) — soit **3,5 %**. Le pivot est marginal en volume.

### 4.1 Le patron technique recommandé : split de plateforme explicite

Le dépôt possède déjà le bon réflexe (`Capacitor.isNativePlatform()` partout), mais il l'applique **au runtime**, pas **au bundler**. Or c'est le bundler qui casse (B1) et qui gonfle le bundle.

```
apps/mobile/src/updater/
  apkUpdater.native.ts      ← l'implémentation Capacitor (jamais dans le bundle web)
  apkUpdater.web.ts         ← no-op typé (mêmes exports)
  apkUpdater.ts             ← ré-export conditionnel (resolve.conditions Vite)
```

Bénéfices : **le build passe sans dépendre de `@capacitor/preferences`**, le bundle web maigrit, et le code natif reste **intact et testable** s'il faut y revenir. Coût : un alias Vite + 2 fichiers.

## 5. Choix d'architecture : trois options

### Option A — `apps/mobile` **est** l'app web (recommandée)

On garde `apps/mobile` comme shell, on construit et déploie son `dist/` en statique. Renommage `apps/mobile` → `apps/web` plus tard, purement cosmétique.

- ✅ **Déjà 90 % vrai** : router `react-router`, écrans, Ionic = web components.
- ✅ **Aucun déplacement de code** : les 38 routes et 45 écrans fonctionnent tels quels.
- ✅ Noms de paquets/alias inchangés (`@aurora/mobile` reste l'entrée).
- ⚠️ Dette de nommage (`mobile` pour du web) — à corriger en P3, sans urgence.
- ⚠️ Ionic en « web pur » laisse du poids (≈ ? Ko, à mesurer — build non rejouable ici).

### Option B — nouveau `apps/web`

Coquille neuve (`vite` + `react-router` + `@aurora/ui`), réimport des pages depuis `apps/mobile/src/pages`.

- ✅ Frontière nette, nommage honnête, bundle maîtrisé (on repart de zéro sur le chrome).
- ✅ Permet de **sortir d'Ionic** progressivement (le shell est déjà 100 % shadcn/Radix hors 5 composants Ionic).
- ❌ **Duplication** de 45 écrans ou déplacement massif → **régression assurée** sur un code dont les tests sont des `node:test` de wiring, pas des tests de rendu.
- ❌ Effort : **~2 à 3 semaines** au lieu de 3 jours.

### Option C — SSR / Next.js

- ❌ Aucun bénéfice ici : app **authentifiée, local-first, post-login**. Le SEO est sans objet, et le rendu serveur est **incompatible** avec un store local SQLite/WASM.
- ❌ Coût de réécriture maximal.

### Recommandation : **A maintenant, B plus tard**

A donne un **déploiement web en 3 jours**. Une fois le produit réellement utilisé en navigateur, la sortie d'Ionic (B) devient une décision **esthétique et de performance**, arbitrable avec des mesures — pas un préalable.

### 9.4 Ce que le lint a réellement trouvé (pas du bruit)

Le passage à `--max-warnings 0` a sorti **trois bugs réels**, pas des questions de style :

1. **`authTab === "signup" || true`** (`OnboardingView.tsx:1112`) — expression **toujours vraie** :
   le bloc OAuth s'affiche aussi en mode « connexion ». Deux lectures possibles (social login
   volontaire, ou reste de debug). **Comportement préservé**, désactivation justifiée sur place —
   c'est au produit de trancher, pas au lint.
2. **`Combobox` sous `@ts-nocheck`** — la directive masquait une vraie erreur : `forwardRef` sur
   `Popover.Root`, qui n'expose aucun nœud DOM et ne déclare pas de prop `ref`. Le `forwardRef`
   était donc à la fois invalide et sans objet (aucun appelant ne passe de ref). Remplacé par un
   composant simple ; `ts-nocheck` supprimé **et** le fichier re-typechecké.
3. **`knowledgeFlags` / `emptyFlags` / `taskFlags`** — trois fonctions minuscules appelant des
   Hooks : violation des règles des Hooks invisible au typecheck (elles sont appelées
   inconditionnellement aujourd'hui, mais rien ne le garantit). Renommées `use*`.

Plus : `AgentBus` recréait son `uiSlice` à chaque rendu — l'ajouter aux deps aurait
démonté/remonté le bus (abonnement global) ; `uiSlice` est désormais mémoïsé.

### 9.6 Ce que « lancer l'app pour de vrai » a révélé

Le build complet étant condamné par la mémoire du sandbox, l'app a été **démarrée**
(`vite dev`) et son graphe **crawlé module par module** via le transformateur à la
demande — même couverture, mémoire plate :

```
modules transformés ......... 1 326
erreurs de transformation ... 0
lien profond /goals/xyz ..... 200 (SPA fallback)
/cette-route-nexiste-pas .... 200 (routeur joignable)
manifest.webmanifest ........ 200 application/manifest+json
sw.js ....................... 200 text/javascript
COOP / COEP ................. same-origin / require-corp
```

Deux défauts réels en sont sortis, tous les deux invisibles au typecheck :

1. **`boot()` n'était borné par rien.** `main.tsx` faisait `await provider.connect()`
   **avant** de peindre, et `connect()` enchaîne `engine.init()` puis
   `waitForFirstSync()` — deux appels sans délai propre. Un réseau qui *pend*
   (portail captif, relay muet) ne rejette pas : le `try/catch` ne se déclenche
   jamais et la page reste blanche **indéfiniment**. Le commentaire « le shell se
   peint toujours » n'était vrai que pour un *rejet*. → course bornée à **5 s**
   (`CONNECT_BUDGET_MS`), avec un `.catch()` sur la promesse d'origine pour ne pas
   laisser fuiter un `unhandledRejection` après expiration.
2. **Un avertissement à chaque build** : `packages/integrations/src/r2-storage.ts`
   charge `node:crypto` par `import(url)` calculée à l'exécution. Le comportement
   est voulu (chemin navigateur mort, EF/Node résolu) mais Vite tente quand même
   de l'analyser. → `/* @vite-ignore */`, qui documente l'intention au lieu de
   laisser un warning dans chaque log de CI.

**Ce qui a été tenté sans succès** : un rendu headless de la coquille (happy-dom +
`ssrLoadModule`) pour prouver le montage React sans navigateur. Abandonné : chaque
échec venait du simulateur, pas du produit (`@antv/f-engine` exige un canvas 2D,
les web components Ionic veulent un vrai `customElements`, WASQLite veut ses
workers). Les 5 parcours Playwright restent seuls juges du rendu — et c'est bien
pour ça qu'ils sont câblés en CI.
